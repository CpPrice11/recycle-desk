# Автооновлення Recycle Desk

Погоджено користувачем 2026-10-24: stable GitHub Releases, перевірка при запуску та кожні 6 годин, автоматичне завантаження й застосування у треї після завершення файлових операцій. Підпис обов’язковий; налаштування зберігаються; автооновлення можна вимкнути. Публікації відбуватимуться в новому репозиторії.

## Реалізація

`self_update 1.3.1` знаходить реліз і перевіряє Ed25519ph-підпис ZIP. `ureq` використовує системний TLS і дозволяє лише HTTPS. Клієнт не містить токена GitHub. Дозволена лише адреса `https://api.github.com/repos/owner/repo/releases/assets/ID` відповідного репозиторію з числовим ID. Для двійкового завантаження передається `Accept: application/octet-stream`, відповідно до [GitHub API](https://docs.github.com/en/rest/releases/assets#get-a-release-asset). Підпис прив’язаний до назви пакета, яка містить версію й платформу.

Архів обмежений 32 MiB; розпакування дозволяє лише `recycle-desk.exe`, `README.md`, `LICENSE`, `THIRD_PARTY_NOTICES.txt`, із межами розміру та без symlink. Шляхи налаштувань не використовуються як цілі оновлення. Непідписаний чи змінений пакет, інший ключ і перейменований підписаний архів відхиляються до заміни EXE.

Підготовлений пакет очікує в UI-стані. Застосування заборонене, доки є відкрите вікно, файлова операція, меню чи модальний діалог. Вимкнення автооновлення видаляє підготовлений пакет. `self-replace` замінює запущений Windows EXE; новий процес через `--wait-for-pid` чекає старого, а потім захоплює single-instance mutex. Під час звичайного виходу застосунок не запускається повторно.

Inno Setup і portable ZIP залишаються. Після нового запуску Inno `DisplayVersion` оновлюється лише за збігу зареєстрованого каталогу з фактичним каталогом EXE. Для portable цей запис не змінюється. Автооновлення потребує доступного для запису каталогу програми.

## Разове налаштування нового репозиторію

1. Додати до репозиторію відкритий файл `resources/update-public.key` разом із кодом. Він уже створений.
2. Зберегти резервну копію приватного ключа `%LOCALAPPDATA%\RecycleDesk\release-signing\private.key` у захищеному місці. Це 64-байтовий keypair. Та сама пара потрібна для наступних релізів. Не комітити його й не надсилати в чат.
3. У GitHub Actions Secrets нового репозиторію додати `RECYCLE_DESK_SIGNING_KEY`: Base64-подання цього приватного keypair. Це не GitHub PAT і не платний сертифікат Windows.
4. Змінювати `version` у Cargo.toml і створювати відповідний тег `vX.Y.Z`. Workflow перевіряє відповідність версії тегу, збирає програму й пакети, підписує `RecycleDesk-X.Y.Z-windows-x64-update.zip`, перевіряє підпис, формує SHA-256 і чернетку Release.
5. Після огляду опублікувати Release. Чернетки та звичайні коміти не запускають оновлення встановлених копій.

Підписаний update ZIP окремий від звичайного portable ZIP: у ньому немає `portable.flag`, налаштувань або інсталятора. У звичайному portable ZIP маркер зберігається.

Секрет читає тільки крок підписування CI: він декодує його в тимчасовий файл, перевіряє відповідність відкритому ключу, підписує та видаляє тимчасовий ключ у `finally`. Значення секрету не друкується. Секрет не передається крокам збірки чи артефактам.

Для іншого власного проєкту нову пару створює `cargo run --example release_sign -- gen-key PRIVATE PUBLIC`. Команда відмовляється перезаписувати наявні ключі. Підпис: `release_sign sign PRIVATE INPUT.zip OUTPUT.zip`.

## Перевірки

Тести: `cargo test --locked --all-targets`. Перевіряються версії, адреси репозиторіїв, safe-idle умови, правильний підпис і негативні сценарії (unsigned, wrong key, rename, tamper).

Ізольований Windows-прогін: `./scripts/test-updater.ps1`. Використовує лише власні файли в `test-output/updater-*`; підписує пакет, встановлює новий тестовий EXE через реальний staging/install-код, перезапускає його з очікуванням PID і повторним захопленням mutex, звіряє SHA-256 контрольних налаштувань. Кошик і основна програма не змінюються.

Результат 2026-10-24: 4 Rust unit tests пройшли (3 updater, 1 локалізація); усі targets/examples компілюються. Додаткова перевірка зміненого staging підтвердила повторну перевірку архіву перед встановленням і відновлення витягнутих файлів із перевіреного підписаного пакета.

Ізольований Windows-прогін пройшов: pinned signature → staging → заміна запущеного EXE → очікування попереднього PID → повторне захоплення mutex → новий процес. SHA-256 контрольного файла налаштувань не змінився. Звіт: `test-output/updater-integration.txt` (локальний, не Git).

Фінальна локальна release-збірка: `target/updater-preview/recycle-desk.exe`, 1 554 944 байти. Підписаний і перевірений пакет: `dist/RecycleDesk-0.1.0-windows-x64-update.zip`, 976 936 байтів. Локальна збірка не має адреси репозиторію, тому мережеві перевірки неактивні.

Створено публічний репозиторій [CpPrice11/recycle-desk](https://github.com/CpPrice11/recycle-desk) і налаштовано `RECYCLE_DESK_SIGNING_KEY` у GitHub Actions Secrets. Відкритий ключ зафіксовано в коді. GitHub CI зібрав MSVC EXE, ZIP та інсталятор, пройшов 4 тести, живий Shell-тест і перевірку підпису. Завантажені ZIP та інсталятор 0.1.0 пройшли SHA-256, живий Shell-тест і встановлення/видалення в окремому каталозі.

Наскрізна перевірка GitHub виявила помилку 0.1.0: бібліотека повертає API URL, а код очікував browser URL. Реліз 0.1.0 повернуто в чернетку. Виправлення [0.1.1](https://github.com/CpPrice11/recycle-desk/releases/tag/v0.1.1) опубліковане, використовує правильний endpoint і заголовок, має окремий регресійний тест (загалом 5 unit tests). GitHub CI повністю пройшов; скачані файли повторно пройшли SHA-256, portable та installer Shell-тести, встановлення/видалення в тестовому каталозі. EXE: 1 542 144 байти, без імпортів VC runtime DLL.

Наскрізне оновлення пройшло: ізольована контрольна версія 0.0.0 із поточним кодом оновлювача отримала публічний stable 0.1.1, завантажила справжній пакет через API, перевірила підпис і повторно перевірила staging, замінила свій запущений EXE. Новий EXE побайтно збігся з опублікованою MSVC portable-збіркою й пройшов живий Shell-тест. Налаштування та `portable.flag` збережені. Це контрольний сценарій попередньої версії, а не дві серійні публічні версії. Локальний звіт: `test-output/github-update-integration.txt`.

Автооновлення Inno-інсталяції та Windows 10 окремо не перевірені. Повний візуальний прогін UI й вимірювання RAM/CPU ще не завершені. EXE/інсталятор не мають Authenticode; підпис ZIP є окремим механізмом.
